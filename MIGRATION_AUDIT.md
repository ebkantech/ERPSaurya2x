However the prior audit's implication that this makes *all* of `search.views` dead is not quite right — `api_chat` and `api_search` (the two JSON views) are separately, directly wired at `omegaerp/urls.py:30-31` as `/api/chat/` and `/api/search/`, and `api_chat` **is** live and used by `AssistantPage.jsx`. Only the two template-rendering views (`index`, `search_view`) and their templates are genuinely and completely unreachable.

### Orphaned templates — not in the table above, but worth flagging

`templates/vendor_portal/` contains **16 template files** (`base.html`, `dashboard.html`, `projects.html`, `daily_updates.html`, `media_gallery.html`, `documents.html`, `issues.html`, `notifications.html`, `review_queue.html`, `review_detail.html`, `forgot_password.html`, `reset_password.html`, `admin_dashboard.html`, `sessions.html`, `login.html`, `user_management.html`). They are pure orphans: safe to delete outright with no view/URL work needed, but flagged here so they aren't mistaken for a live legacy surface during planning.

## Section 2 — Dual-mode views (render OR JsonResponse from the same function)

**None found.** Every `views.py` in the project (`core`, `administration`, `purchase_orders`, `purchase_orders/quotation_views`, `vendors`, `reports`, `search`, `tasks`, `accounts`) was read in full and searched for:
- `request.headers.get('X-Requested-With')` / `is_ajax()` patterns
- `Accept` header branching
- `?format=json` or similar query-param branching
- any single function body containing **both** a `return render(...)` and a `return JsonResponse(...)`

No matches anywhere in the codebase (a repo-wide grep for `X-Requested-With|is_ajax|HTTP_ACCEPT|format.*json` across all `.py` files also returned zero hits). The codebase cleanly separates HTML-rendering views from JSON-returning views into **different, dedicated view functions**, even when they cover the same data (e.g. `purchase_order_detail` vs `purchase_order_detail_api`, `vendor_assignment_list` vs `assignments_api`). This is good news for the migration: no view needs to be *split* — every legacy screen's JSON dependents (if any) are already isolated in their own functions and can be identified purely by "which JSON endpoints does this URL prefix/screen already have" (Section 1's JSON-endpoints column) rather than by disentangling a shared function.

The one screen that comes closest to "multi-mode" is `reports.views.report_center` (`reports/views.py:13`), which branches its **queryset shape** seven ways via `?type=`, but always returns rendered HTML regardless — it never returns JSON, so it doesn't qualify as dual-mode by the render-vs-JSON definition.

## Executive summary — highest-value findings for planning

1. **`core.views.index` (the Django dashboard.html view) is already dead code** — shadowed by the React catch-all at `omegaerp/urls.py:44`, which comes before `include('core.urls')` at line 47. No migration work needed there; it's already effectively retired.
2. **11 non-`/api/` JSON endpoints exist**, 5 of which are live dependencies of the current React app (`MaterialList.jsx`, `QuotationBuilder.jsx`, `QuotationDetail.jsx`, `VendorCreate.jsx`). A phased removal must special-case `core/urls.py`'s `materials/master/*` and `vendors/register/` routes and `purchase_orders/urls.py`'s `bulk-generate/check/` route — do not delete these when retiring the HTML pages that share their URL prefix.
3. **Zero dual-mode views** — HTML and JSON concerns are already cleanly separated per view function everywhere in the codebase. Screen-by-screen removal can proceed function-by-function without needing to "split" anything.
4. **Two confirmed runtime bugs, independent of migration:** `administration.views.whatsapp_settings_view` (`administration/views.py:511`) references an unimported `WhatsAppConfigurationForm` (NameError on every hit), and `vendors.views.authorization_dashboard_api` (`vendors/views.py:740`, bound at `/vendor-control/api/summary/`) calls an unimported `get_accessible_task_queryset` (NameError for admin-like users). Worth fixing or explicitly deciding to just delete rather than migrate.
5. **`purchase_order_detail` (`purchase_orders/views.py:446`) is the single highest-risk screen to decompose** — 9 POST action branches, 9 different models written, multiple file uploads, would need ~8 new granular JSON endpoints to fully replace (the existing `purchase_order_detail_api` only covers the read side).
6. **`purchase_orders` app has zero authentication on any of its 4 template views** (`procurement_dashboard`, `purchase_order_master`, `purchase_order_bulk_generator`, `purchase_order_detail`) and `vendors.views.vendor_master` (`/procurement/vendors/`) is likewise open — worth deciding whether to add auth before or as part of the React cutover, since there's no Django middleware providing a blanket login gate (`omegaerp/settings/base.py` `MIDDLEWARE` has only standard `AuthenticationMiddleware`, no login-required middleware).
7. **Two parallel vendor-create UIs write to the same `core.models.Vendor` table**: `core.views.register_vendor` (full KYC form, used by React's `VendorCreate.jsx`) and `vendors.views.vendor_master`'s POST branch (`VendorMasterForm`, shorter field set, no React equivalent). Consolidate deliberately rather than assuming one supersedes the other.
8. **`administration` app (19 screens) collapses to a 6-tab `AdminPanel.jsx`** in React today, and all 6 of those tabs are still mock/hardcoded with zero API calls — this is the single largest screen-count-to-React-page compression in the app and the biggest true migration lift, not just a data-wiring exercise.
9. **`templates/vendor_portal/` (16 files) is entirely orphaned** — no view anywhere renders them. Safe to delete with no URL/view archaeology required.
10. **`search/urls.py` is confirmed never included** in `omegaerp/urls.py`, but `search.views.api_chat` and `api_search` are separately wired directly at `/api/chat/` and `/api/search/` at the root — `api_chat` is live (used by `AssistantPage.jsx`), `api_search` exists but is currently unused by React. Only `search.views.index`/`search_view` and their two templates are fully dead.
